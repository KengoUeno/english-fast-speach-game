# 追いつけEnglish

## 概要

「追いつけEnglish」は、画面を流れていく英語の説明文を**声に出して読み切る**スピードに挑戦する、ローカル2人以上のパス&プレイ・パーティーゲームです。読み手は自動で流れる英文に追いつきながら音読し、聞き手はその音読だけを頼りに「何の単語を説明しているか」を当てます。

英語学習アプリにありがちな「一人で黙々と反復する」体験ではなく、**焦りと笑いを含んだ音読体験**をパーティーゲーム化することで、発話量と読解速度を同時に鍛えます。シリーズ第1弾「察してEnglish」（タブーワード方式の伝言ゲーム）の姉妹作であり、ブランド・技術スタック・マネタイズ構造を共有します。

---

## ターゲットユーザー

| セグメント | 利用シーン |
|---|---|
| 中高生・大学生の友人グループ | 休み時間、放課後、部室での数分間の暇つぶし |
| 英会話スクール・学校の英語教師 | 授業のアイスブレイク、音読トレーニングの導入 |
| 家族（親子） | 食卓や車内での親子英語遊び |
| 英語学習コミュニティ・社会人サークル | オフ会・勉強会のウォームアップ |

**共通する前提**
- 1台のスマートフォンを回して遊ぶ（サーバー・アカウント・通信対戦は不要）
- 英語レベルは中学〜高校程度。「読めるが、速くは読めない」層がコアターゲット
- 1ゲーム1〜5分で完結し、何度もリトライしたくなること

## コアゲームループ

### 役割

| 役割 | 人数 | やること | 画面 |
|---|---|---|---|
| 読み手（Reader） | 1人 | 端末を持ち、流れる英文を声に出して読む | 見る |
| 聞き手（Guesser） | 1人以上 | 音読だけを聞いて、お題の単語を当てる | **見ない** |

端末は読み手が持つ。お題の単語と説明文はどちらも画面上にあるため、聞き手は画面を覗いてはいけない（物理的な運用ルール。前作と同じパス&プレイ方式）。

### 1問の流れ

```
[お題カード表示]
   ├ お題単語（例: ゾウ / Elephant）        ← 読み手だけが見る
   └ 説明文（英文 8〜20語）                  ← 自動で「流れる」
        ↓
[フロー演出開始] 説明文の先頭から順にハイライトが進む
        ↓
   ┌────────────────────────────────┐
   │ 読み手: ハイライトに追いつきながら音読      │
   │ 聞き手: 音読を聞いて単語を推測              │
   └────────────────────────────────┘
        ↓
   ┌── 聞き手が正解 → 誰かが「✓ CORRECT!」をタップ → +1点 → 次のお題
   ├── 読めない/わからない → 「SKIP」をタップ → 加点なし → 次のお題
   └── ハイライトが最後まで到達 + 猶予時間切れ → 自動SKIP → 次のお題
```

### スコアと制限時間

- **全体タイムアタック制**（前作 `useGameEngine` の構造を踏襲）。デフォルト60秒、開始前に選択可能。
- 制限時間内にできるだけ多くのお題を正解させる。**正解1件につき +1点**、開始スコアは0点。
- ゲーム開始時に「3 → 2 → 1 → GO!」のカウントダウン演出を挟む（前作踏襲）。
- 全体タイマーが0になった時点で即ゲーム終了 → リザルト画面へ。

### 「流れる」速度のルール（本作の中核）

説明文が流れる基本速度は**説明文の単語数から自動計算する**（説明文そのものの長さが体感難易度になる、という考え方は維持）。加えて、**スタート設定画面で「簡単 / 普通 / 難しい」の3段階からスクロール速度を選べる**（ユーザーからの追加要望により導入。プレイ人数・英語レベルに合わせて速度を調整できるようにする）。

説明文は最初から全文が見えているわけではない。**画面下から上へ、平面のまま一定速度でスクロールアップしていく**演出とする（単語単位のハイライト表示は廃止し、本文全体が一体となって流れていく）。

> 補足: 当初はスター・ウォーズ映画のオープニングのような3D遠近法クロール（奥の消失点に向かって傾き・縮小しながら流れる演出）を採用したが、実機での確認の結果「速く正確に読む」という本作のコア体験と相性が悪く可読性を損なうと判断し、**3D遠近法は廃止して平面のスクロールアップに戻した**（ユーザー承認済み）。スクロールの方向（下→上）自体は変更していない。

```
フロー時間(ms) = LEAD_IN + 単語数 × MS_PER_WORD
  LEAD_IN     = 1000ms   （読み始めるまでの助走。速度レベルによらず共通）
  MS_PER_WORD = 速度レベルに応じて変化（下表）
  下限        = 4000ms
```

| 速度レベル | MS_PER_WORD | 目安wpm | 8語 | 12語 | 20語 |
|---|---|---|---|---|---|
| 簡単 | 900ms | ≒67 wpm | 8.2秒 | 11.8秒 | 19.0秒 |
| 普通（デフォルト） | 650ms | ≒92 wpm | 6.2秒 | 8.8秒 | 14.0秒 |
| 難しい | 480ms | ≒125 wpm | 4.8秒 | 6.8秒 | 10.6秒 |

> 補足: 初期値（簡単550ms/普通400ms/難しい280ms）はユーザーの実プレイの結果「難易度が高い（速すぎる）」と判断され、3回にわたり段階的に減速した（現在の値）。

- 速度レベルはスタート設定画面で選択し、選択値はゲーム開始時に固定される（プレイ中の切り替えはしない）
- デフォルトは「普通」（従来のMS_PER_WORD=400msと同一。既存のバランスを崩さない）
- 上記の数値は初期値であり、プレイテストで調整する前提の**チューニング可能なゲームパラメータ**として扱う

- 説明文はLEAD_IN経過後、画面下から現れて画面上へ向かって一定速度で平面のままスクロールアップする（傾き・縮小・遠近感は付けない）。文字サイズ・濃さは終始一定とする。
- 説明文全体のスクロールが完了し、フロー時間が経過した後、**猶予時間 3秒**（GRACE）を与える。この間も CORRECT / SKIP は受け付ける。
- 猶予も過ぎたら自動的に次のお題へ進む（スキップ扱い、加点なし）。
- 上記の定数はプレイテストで調整する前提の**チューニング可能なゲームパラメータ**として扱う。

### 正解判定の方針

- 判定は**人力のみ**。音声認識・発音採点は行わない。
- 将来的にも音声認識は導入しない。マイク権限を要求しないことを設計上の前提とする（ストア審査・プライバシーポリシーの簡素化にも寄与）。

## マネタイズ方針

前作「察してEnglish」の `keywordSets` パターンを**そのまま踏襲**する。

- **無料スターターパック 1つ**（例: 日常会話 30問）で、課金なしでもゲームが成立する
- **テーマ別パックを買い切りで販売**（非消耗型 / non-consumable）
  - 想定テーマ: 旅行、ビジネス、日常会話、動物、スポーツ、食べ物 など
  - 1パックあたり 100問程度、価格は前作と同水準（100〜300円）
- 課金基盤は **RevenueCat**。iOS / Android の両ストアに同一の商品IDで登録する
- パック内容はビルド時にバンドルする（前作同様、HTTPフェッチはしない）。ロック/アンロック判定は購入状態のみで行う
- サブスクリプション・広告・消耗型アイテムは導入しない

### パックの一時共有機能（ホスト/ゲスト方式、前作からの新規追加）

本作は複数人で同じ場に集まって遊ぶパーティーゲームであるという特性を踏まえ、**パックを購入済みのプレイヤー（ホスト）が、その場に居合わせた別のプレイヤー（ゲスト。アプリはインストール済みだがそのパックは未購入）の端末で、一時的にそのパックを使えるようにする機能**を設ける。「1人が買えば全員が永続的に使えるようになる」ことは避け、あくまでその場限りの一時的な解放とする。

**方式: オフライン署名コード（サーバー不要）**

- ホスト端末は、「共有コードを発行する」という**単一の操作**（特定のパックを選ぶ操作ではない）で、**発行時点でホストが購入済みの全パックの集合＋発行時刻から3時間後の有効期限**を含む英数字コード（**8文字程度**、ユーザー指定。手入力のしやすさを優先）をその場で生成し、画面に表示する。生成・検証ともにネット接続は不要（署名検証用の鍵はアプリに埋め込む）
  - **パックごとにコードを発行・入力させるのはUXが悪いため、1回のコード発行・1回のコード入力で、ホストが持つ購入済みパックすべてを一括で一時解放する**（ユーザー要望により、当初の「パック単位」設計から変更）
  - 8文字という長さは、10〜14文字の場合と比べて偽造耐性（総当たりでの正規コード捏造への耐性）が下がるトレードオフがあるが、コードの一時性（3時間で自動失効）と本作がパーティーゲームでありハイリスクな不正利用の標的になりにくいことを踏まえ、**手入力のしやすさを優先する仕様としてユーザー承認済み**とする
- ゲスト端末は、アプリ内の「コードを入力」画面にそのコードを**手入力**する（QRコード等は本機能では対象外）。アプリ内蔵の鍵で署名を検証し、有効ならコードに含まれる**全パック**をそのゲスト端末上で一時的にプレイ可能にする。成功時はどのパックが解放されたかを（複数ある場合は全て）表示する
- **有効期限は発行から3時間**。期限を過ぎるとコード自体が無効になり、含まれていた全パックが自動的に再ロックされる。コードが漏洩・使い回されても期限を過ぎれば無効なため、実質的に「その場・その時間帯限り」の共有にとどまる
- 同じコードは、有効期限内であれば**複数のゲスト端末から同時に利用できる**（グループ全員が同じコードを入力する想定）。発行回数や同時解放人数の制限は設けず、時間経過による自動失効のみで一時性を担保するシンプルな設計とする
- ホストが**何も購入していない**場合は、共有コードを発行しても意味がないため発行導線自体を出さない（またはボタンを無効化する）

## 技術スタック（制約: 前作と同一構成を踏襲すること）

本プロジェクトは姉妹プロジェクト `taboo-english-game` と**同じ技術スタック・同じモノレポ構成を踏襲する**。理由は、開発ノウハウ・ストア申請ノウハウ・コンポーネント資産をそのまま再利用できるため。

- **モノレポ**: npm workspaces（`apps/*`, `packages/*`）
- **モバイル**: Expo（React Native）+ expo-router
- **ゲームロジック**: `packages/game-core` に切り出し、モバイル/Web で共有
- **課金**: RevenueCat（`react-native-purchases`）
- **Web**: 静的HTML（ランディングページ・プライバシーポリシー・サポートページ配信用、GitHub Pages で公開）
  - 当初は前作同様 Next.js を想定していたが、本作は**Web版アプリを持たない**（モバイルのみ）ため、教訓集の方針（モバイルのみの構成なら Vercel ではなく GitHub Pages を使う）に従い、ビルド不要の静的サイトに変更した（Sprint 5 で決定）
- **フォント**: `@expo-google-fonts/*`

詳細な設計（型定義、状態管理、ディレクトリ配置など）は Generator に委ねる。

**必読**: ストア公開・App内課金の実装前に `docs/mobile-app-release-lessons.md`（前作のリリースで得た教訓集）を参照すること。

## スプリント ロードマップ

| Sprint | テーマ | 主なスコープ |
|---|---|---|
| **Sprint 1** | コアゲームループ | モノレポ基盤、お題データモデル、流れる説明文演出、1台ローカル対戦が最後まで遊べる状態 |
| Sprint 2 | 体験の作り込み | ホーム / 遊び方 / スタート設定の各画面、リザルト演出、レビュー訴求（リプレイ機能はユーザー判断で不要と決定し対象外） |
| Sprint 3 | マネタイズ | RevenueCat 連携、ストア画面、テーマ別パック追加（有料4パック × 100問）、パック選択、購入の復元 |
| Sprint 4 | パックの一時共有 | 共有コードの発行（ホスト）、コード入力による一時解放（ゲスト）、3時間の有効期限と自動再ロック、不正コードの拒否、購入状態との分離 |
| Sprint 5 | リリース準備 | アイコン・スプラッシュ、プライバシーポリシー／サポート／ランディングの静的サイト、アプリ内の法務リンク、`app.json`/`eas.json`/環境変数の整備、ストア掲載情報の原稿、リリース手順書 |

> Sprint 3 は当初「RevenueCat 連携とパックの一時共有」を1本にまとめる想定だったが、(1) 一時共有が「購入済みパックのみ共有可能」という Sprint 3 の成果物に一方向に依存すること、(2) 課金側のリスクが外部依存（ストア設定・実機）である一方で共有側のリスクは自前ロジック（署名・期限判定）であり、混在させると不合格時の切り分けが困難になること、(3) 合計の契約項目が40を超え部分的な完成を「完了」と誤認しやすいこと、(4) 「画面に表示する全商品を初回審査でまとめて提出する」（前作の教訓6）ためにラインナップの確定を先に凍結したいこと、を理由に **Sprint 3（通常課金）と Sprint 4（一時共有）に分割**した。リリース準備は Sprint 5 に繰り下げている。

> Sprint 5 は**分割せず1本**とする。ただし成果物の半分が自動検証の外（実機・ストアコンソール・RevenueCat ダッシュボード）にあるため、スプリント内部を **5-A（Evaluator が Playwright / ファイル検査で合否を出す範囲）** と **5-B（ユーザーが手作業で行う、合否判定対象外の作業リスト）** の2層に分けている。Evaluator は 5-B の未完了を理由に不合格を出してはならない。

各スプリントの契約は `docs/sprints/sprint-N.md` を参照。
