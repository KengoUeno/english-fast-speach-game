## Sprint 5: リリース準備 ―「審査に出せる状態」まで、リポジトリ側を完成させる

### ゴール

Sprint 1〜4 でアプリ本体は「買って、遊んで、その場で共有できる」ところまで完成した。Sprint 5 は**ストアに出すために必要な、アプリ本体以外の成果物**を揃えるスプリントである。

具体的には、(1) アプリアイコン・スプラッシュ・各種アイコン画像、(2) ストア申請に必須のプライバシーポリシー／サポートページ、(3) それらを配信する静的Webサイト（ランディングページを兼ねる）、(4) ストア掲載情報の原稿一式、(5) ビルド・申請に必要な設定ファイル（`app.json` / `eas.json` / 環境変数）、(6) ユーザーが手作業で行うストア申請の手順書、を作る。

**このスプリントの最大の特徴は、成果物の約半分が Evaluator（Playwright / Expo Web）では検証できない領域にあることである。** 実機でのアイコン表示、ストアコンソールでの申請、RevenueCat ダッシュボードでの商品登録、実決済のテストは、いずれも自動検証の外にある。したがって本スプリントは**契約を2層に分け**、Evaluator の合否判定は「リポジトリ内に存在し、ブラウザまたはファイル検査で確認できるもの」に限定する。外部作業は合否対象外の**ユーザー作業リスト**として明記する。

---

### スコープ判断の理由

#### 分割するか、1スプリントのままか → **1スプリントのまま進める**

検討の結果、Sprint 5 は分割せず1本のスプリントとして扱う。理由は以下の4点。

| 判断 | 理由 |
|---|---|
| **Evaluator が検証できる範囲だけを取り出すと、Sprint 3 / Sprint 4 と同程度の分量に収まる** | 自動検証の対象になるのは「静的サイト3ページ」「アイコン類とその設定」「アプリ内の法務リンク」「原稿・設定ファイルの妥当性」で、契約項目は30件強。Sprint 3（28件）・Sprint 4（30件）と同水準であり、分割の閾値（契約40件超）に達しない |
| **成果物が相互に依存していて、切ると往復が増える** | プライバシーポリシーの公開URLが決まらないとアプリ内リンクもストア掲載情報も書けない。アイコンが決まらないとランディングページもストア素材も作れない。依存が循環に近く、Sprint 3→4 のような「一方向の依存」で切れない |
| **外部作業は元々 Evaluator の管轄外であり、スプリントとして切っても合否判定ができない** | 「ストア申請スプリント」を別に立てても、Evaluator は1項目も検証できず、スプリントの体裁を保てない。これは**スプリントではなくチェックリスト**として持つべきもの |
| **教訓6（画面に出ている全商品を初回審査でまとめて出す）への対応は、ラインナップが凍結済みの今まとめてやるのが最も安全** | Sprint 3 で4パックに凍結済み。申請原稿を分割して別スプリントに送ると、「1商品だけ先に出す」という前作の失敗を再現しやすい |

ただし**スプリント内部は2層に分ける**。`5-A` は Evaluator が検証し合否を出す範囲、`5-B` はユーザーが手作業で行い Evaluator が一切判定しない範囲とする。Evaluator は `5-B` の未完了を理由に不合格を出してはならない。

#### ランディングページを Next.js ではなく静的HTMLで作る

spec.md の技術スタックには「Web: Next.js（ランディングページ・プライバシーポリシー配信用）」とあるが、**本スプリントでは Next.js アプリ（`apps/web`）を新設せず、素の静的HTMLサイトとして作る**方針に変更する。理由は教訓集の「開発着手前にやること」に明記された次の一点。

> プライバシーポリシー/サポートURLのホスティングは、Web版を作らない(モバイルのみの)構成ならVercelではなく**GitHub Pages**を使う。アプリのリポジトリに直接置け、追加のアカウント・ダッシュボードが不要になる（察してEnglishはWeb版が先にあったのでVercelを使ったが、それは今回限りの事情）。

本作は前作と違い**Web版アプリを持たない**（`apps/` はモバイルのみ）。ここで Next.js を導入すると、ビルドパイプライン・Vercelアカウント・依存関係が増えるだけで、静的な3ページを配るという目的に対して過剰である。静的HTMLなら GitHub Pages にそのまま置け、Playwright での検証も容易になる。spec.md の記述はこの判断に合わせて更新すること（Generator ではなく Planner の責務として、本ファイルをもって決定とする）。

#### Sprint 5 に含めるもの

| 含めるもの | 理由 |
|---|---|
| アプリアイコン・Androidアダプティブアイコン・スプラッシュ・favicon | ストア申請の必須素材。アルファチャンネルや寸法の要件を外すと EAS ビルドや申請がそこで止まる（教訓7の系） |
| プライバシーポリシーページ | iOS / Android 両方で**URLの提出が必須**。これがないと審査提出画面に進めない |
| サポート（お問い合わせ）ページ | Apple はサポートURLを必須項目として要求する |
| ランディングページ | 上2ページと同じサイトに同居させる。単独で作るコストはほぼゼロで、ストア公開後の導線にもなる |
| アプリ内からの法務リンクとバージョン表示 | ストア掲載URLだけでも審査は通るが、問い合わせ対応にアプリ内のバージョン表示が要る。Sprint 2 の「押しても何も起きないプレースホルダーを置かない」原則に従い、実URLを開くものだけを置く |
| `app.json` / `eas.json` / 環境変数の整備 | 教訓3（環境変数はビルド前に確定）・教訓7（iPad非対応）・教訓4（バージョン運用）に直結。ここの不備は「ビルドやり直し」という最も高いコストで返ってくる |
| ストア掲載情報の原稿（`docs/store-listing.md`） | Apple は審査提出の前提として店頭情報一式を要求する。文字数上限のある項目が多く、コンソール上で書き始めると溶ける |
| ユーザー作業の手順書（`docs/release-checklist.md`） | 教訓6・6b の申請手順、クローズドテスト12人×14日、Paid Applications Agreement など、忘れると数日〜数週間の遅延になる項目を1枚にまとめる |

#### Sprint 5 から外すもの

| 外すもの | 理由 |
|---|---|
| `apps/web`（Next.js アプリ）の新設 | 上記の通り静的サイトに置換 |
| 実機ビルド・ストア申請・実決済テスト・RevenueCat ダッシュボード設定 | Evaluator が検証できない。`5-B` のユーザー作業リストへ |
| スクリーンショット画像そのものの制作 | 実機/シミュレータのキャプチャが必要で、リポジトリ内では完結しない。要件表（必要サイズ・枚数）だけを `5-A` で用意し、撮影は `5-B` |
| パックの追加、ハイスコア、効果音・触覚フィードバック | spec.md で優先度「低」。初回リリース後の別リリースで扱う |
| 多言語対応（英語のストア掲載情報） | 配信地域は全世界だが、初回は日本語のみで提出する（前作と同じ運用）。必要になった時点で追加 |

### 検証環境

Evaluator は次の2つを使って検証する。

1. **静的サイト**: リポジトリルートで `npm run site` を実行すると、`site/` 配下がローカルの固定ポートで配信される。Playwright はこのURLを開いて検証する
2. **Expo Web**: これまで同様 `npm run web`

静的サイトは GitHub Pages のプロジェクトページ（`https://<user>.github.io/<repo>/` のような**サブディレクトリ配下**）で配信される前提とする。ルート直下を前提にした絶対パス（`/privacy-policy/`）を使うとリンクが壊れるため、Evaluator はサブパス配信でもリンクが機能することを確認する。

### 5-A: Evaluator が検証する範囲

#### 実装する成果物

- **成果物A: アイコン・スプラッシュ一式**
  `apps/mobile/assets/` に、アプリアイコン（1024×1024 PNG・アルファなし）、Androidアダプティブアイコンのフォアグラウンドとモノクロ（各1024×1024 PNG・透過あり）、スプラッシュ用画像、favicon を配置する。デザインは `docs/design-tokens.md` の「マスコットの方向性」（口を大きく開けて声を出している表情、`cream` の顔に `orange` の口、ネイビー背景）と `docs/design-references/satteenglish-icon.png` に従い、**前作とシリーズで揃って見えること**を最優先する。アイコン画像の制作は Designer フェーズの担当とする。

- **成果物B: 公開静的サイト（`site/`）**
  GitHub Pages で配信する静的サイトを作る。構成は次の3ページ。
  - `site/index.html` — ランディングページ。アプリ名・キャッチコピー・ゲームの説明（読み手/聞き手の役割）・収録パックの紹介・ストアバッジ・法務ページへのリンク
  - `site/privacy-policy/index.html` — プライバシーポリシー
  - `site/support/index.html` — サポート／お問い合わせ／よくある質問
  配色・書体は `docs/design-tokens.md` に従う。ビルド不要の素のHTML/CSSとし、外部フレームワークに依存しない。ルートの `package.json` にローカル配信用の `site` スクリプトを追加する。
  プライバシーポリシーの本文は前作 `C:\Users\uenokengo\dev\taboo-english-game\legal\privacy-policy\index.html` を下敷きにしてよいが、**本作固有の事情（音声認識を使わずマイク権限を要求しないこと、パックの一時共有がオフライン完結でサーバー送信を行わないこと）を必ず反映する**。

- **成果物C: アプリ内の法務リンクとバージョン表示**
  ホーム画面の下部に、プライバシーポリシー・お問い合わせへの控えめなリンクと、アプリのバージョン表示を置く。リンク先URLは**コード内の1箇所**（例: `apps/mobile/lib/links.ts`）に定義し、画面にハードコードしない。同じURLを `docs/release-checklist.md` にも記載する。Web環境でリンクを押してもクラッシュしないこと。

- **成果物D: ビルド・申請用の設定ファイル**
  `app.json` にアイコン／アダプティブアイコン／スプラッシュ／favicon を設定し、`eas.json` を新規作成する（`development` / `preview` / `production` と `submit`）。RevenueCat のAPIキーなど必要な環境変数を `.env.example` に列挙する。教訓3に従い、**「本番キーは最初の production ビルドの前に確定させる」**旨を手順書に明記する。

- **成果物E: ストア掲載情報の原稿（`docs/store-listing.md`）**
  両ストアのコンソールにコピー&ペーストできる完成原稿を書く。文字数上限のある項目はすべて**上限内に収まった実際の文章**とし、「後で書く」を残さない。スクリーンショットの必要サイズ・枚数の要件表も含める。**4つの有料パック全ての商品登録情報（商品ID・表示名・説明・価格）を1つの表にまとめ、教訓6「画面に表示されている全ての App内購入商品は初回審査提出時に全部まとめて含める」を注記として書く。**

- **成果物F: リリース手順書（`docs/release-checklist.md`）**
  `5-B` のユーザー作業を、着手順・所要期間つきのチェックリストにする。教訓集の該当項目（クローズドテスト12人×14日、Paid Applications Agreement、教訓6b の複数IAPをまとめる手順、versionCode のプロモート運用、ビルド失敗時の外部要因、レビューポップアップは本番でのみ確認可）を本作の文脈に落として書く。

- [ ] 教訓6b の「App Store Connect で複数のApp内購入を1つの提出にまとめる手順」が、本作の4商品に当てはめた形で手順として書かれている

**堅牢性・回帰**

- [ ] Expo Web でホーム・遊び方・スタート設定・プレイ・リザルト・ストア・共有の各画面を一巡しても、未処理例外がコンソールに出ない
- [ ] 静的サイトの3ページを開いてもコンソールエラー（404を含む）が発生しない
- [ ] Sprint 1〜4 の契約が引き続きすべて満たされている（カウントダウン、単語数と速度選択に応じた流れる説明文、CORRECT / SKIP の加点、猶予時間と自動スキップ、リザルト演出とレビュー訴求のカウント、ストア画面の購入・復元の「準備中」挙動とパック選択、共有コードの発行・入力・期限切れ・不正コード拒否が回帰していない）

---

### 5-B: ユーザーが別途行うべき作業（Evaluator の合否判定対象外）

以下は**リポジトリの外**で行う作業であり、Playwright では一切検証できない。Evaluator はこれらを判定対象にせず、`5-A` の合格後にユーザーが自身で実施する。詳細な手順は `docs/release-checklist.md` に記載される。

#### B-1. ホスティングの用意（`5-A` の公開URL確定の前提）

- [ ] GitHub リポジトリを作成し、`site/` を GitHub Pages で公開する（教訓: モバイルのみの構成では Vercel ではなく GitHub Pages）
- [ ] 公開URLを確定し、`5-A` で定義したアプリ内リンクの定数・`docs/store-listing.md` の記載と一致していることを目視で確認する
- [ ] 公開後、実際のURLでプライバシーポリシーとサポートページが表示されることをブラウザで確認する

#### B-2. ストアアカウントとアプリ枠（**最優先で着手**）

- [ ] Google Play Console でアプリを作成する
- [ ] **クローズドテストのテスター12人を集め、14日間の連続テストを開始する**（新規アカウントの本番リリース必須条件。最長のボトルネックなので、他の作業と並行して最初に着手する）
- [ ] App Store Connect でアプリを作成し、`ascAppId` を取得して `eas.json` の `submit` に設定する
- [ ] **Paid Applications Agreement（有料アプリ契約）を有効化する**（未有効だと実機で購入が必ず失敗する。前作で1ビルド分を無駄にした）
- [ ] EU デジタルサービス法（DSA）の取引者情報が、アカウントレベルで既に登録済みか確認する。未登録の場合、**公開される情報であることを理解した上で**入力する（教訓8）

#### B-3. RevenueCat と App内課金の登録

- [ ] RevenueCat でプロジェクトを作成し、iOS / Android のアプリを紐付ける
- [ ] App Store Connect と Google Play Console の両方に、**4商品すべて**を同一の商品ID（`travel_pack_1` / `business_pack_1` / `animals_pack_1` / `food_pack_1`）・非消耗型・100円で登録する
- [ ] RevenueCat 側で Offering を作成し、4商品すべてを `availablePackages` に含める（`purchaseProduct` ではなく `purchasePackage` を使う実装のため、Offering への登録が必須）
- [ ] 本番APIキーを取得し、**最初の production ビルドを走らせる前に** EAS の環境変数として設定する（教訓3: 後から変えても既存バイナリには反映されない）

#### B-4. 素材の制作とストア掲載

- [ ] `docs/store-listing.md` の要件表に従い、iOS / Android それぞれのピクセルサイズでスクリーンショットを撮影・作成する（両ストアで流用不可）
- [ ] Google Play のフィーチャーグラフィックを作成する
- [ ] 両ストアのコンソールに、`docs/store-listing.md` の原稿をコピー&ペーストして掲載情報を埋める
- [ ] Google Play の「データ安全性」フォームに回答する（収集データ: 購入情報のみ／広告ID: 使用しない／マイク等の権限: なし）
- [ ] App Store Connect のプライバシー質問に回答する

#### B-5. ビルドと実機確認

- [ ] `eas build --platform ios|android` で production ビルドを作成する（Xcode / Android Studio のローカルインストールは不要）
- [ ] **実機でアプリアイコンとスプラッシュの見え方を確認する**（ホーム画面での視認性、Androidの円形・角丸マスクでの欠け、ダークな壁紙での埋没）
- [ ] EAS 開発ビルド（`--dev-client`）を実機に入れ、**RevenueCat の購入・復元を実際に動かして確認する**（Expo Go では `react-native-purchases` が動かないため検証不可）
- [ ] 実機で共有コードの発行・入力を確認する（Web で検証済みだが、キーボード・クリップボードの挙動は実機固有）
- [ ] ビルドが `Gradle build failed` 等で落ちた場合、まずログの実際のエラー箇所を見る。Maven Central の `429` など外部要因なら設定をいじらず時間を置いて再試行する（教訓5）

#### B-6. 審査提出（**最も事故が起きやすい工程**）

- [ ] **ストア画面に表示している4つの有料パックすべてを、初回の審査提出に含める。**「1つだけ先に出して後から足す」は前作が Guideline 2.1(b) App Completeness で却下された原因であり、絶対に行わない（教訓6）
- [ ] App Store Connect で4商品を1つの提出にまとめる際は、各商品の詳細ページから**個別の下書きを先に削除**して「どの提出物にも属さない状態」に戻し、その上で一覧のチェックボックスで4つ全部を選んで「審査用に追加」する（教訓6b。一覧のチェックボックスがグレーアウトして詰まりやすい）
- [ ] 動作確認済みのビルドを別トラックへ展開するときは、新規リリースの作成ではなく**「プロモート」**を使う（教訓4: versionCode は使い回せない）
- [ ] 審査提出後、却下された場合はメッセージの Guideline 番号を確認し、教訓集に照らして原因を切り分ける

#### B-7. リリース後

- [ ] ストア評価ポップアップは**本番版でのみ動作する**。TestFlight やクローズドテストで表示されなくても実装ミスとは限らない（教訓10）。本番リリース後、3回プレイしてから挙動を確認する
- [ ] 本番リリース後、実決済（Sandbox ではない実際の購入）で4パックすべての購入と復元を確認する
- [ ] 今回のリリースで新たに得た教訓を `docs/mobile-app-release-lessons.md` に追記する
