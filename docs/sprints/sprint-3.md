## Sprint 3: マネタイズ ―「遊べるお題が増える」導線を、課金として成立させる

### ゴール

無料スターターパック30問だけの状態から、**テーマ別の有料パックを買って遊べる**状態にする。RevenueCat を組み込み、ストア画面でパックを購入・復元でき、スタート設定画面で所有パックを選んで遊べるところまでを完成させる。

あわせて、前作の却下事例（`docs/mobile-app-release-lessons.md` 教訓6）を踏まえ、**「ストア画面に表示するパックの顔ぶれ」をこのスプリントで確定させる**。画面に出ている商品は初回審査提出時に全部まとめて審査に出す必要があり、後から1つずつ足す運用は取れないため、リリース準備（Sprint 5）より前に固定しておく。

---

### スコープ判断の理由

#### なぜ「通常課金」と「パックの一時共有」を分けたのか

ユーザーからの依頼時点では Sprint 3 に「通常の課金機能」と「パックの一時共有機能」の2つが挙がっていたが、**2つのスプリント（Sprint 3 = 通常課金 / Sprint 4 = パックの一時共有）に分割する**と判断した。理由は以下の4点。

| 理由 | 内容 |
|---|---|
| **依存関係が一方向に明確** | 一時共有は「購入済みパックのみ共有可能」という前提の上に成り立つ。パックのデータモデル・所有状態の判定・ロック/アンロックUIが確定していないと、共有機能の解放対象も「一時解放中」の表示も定義できない。逆は成立しない（共有がなくても課金は完結する） |
| **リスクの種類が違い、混ぜると切り分けられない** | 課金側のリスクは**外部依存**（RevenueCat設定、ストアコンソールの商品登録、実機でしか確認できない領域）。共有側のリスクは**自前ロジック**（署名・エンコード・期限判定）で、こちらは Expo Web / 単体テストで完全に検証できる。1スプリントに混ぜると、Evaluator が不合格を出したときに「ストア設定の問題」か「署名ロジックの問題」かを切り分けづらく、フィードバックループが伸びる |
| **量がスプリント2本分ある** | 課金側だけで「パックのデータモデル拡張＋有料4パック×100問のお題データ＋ストア画面＋RevenueCat連携＋パック選択UI」があり、これ単体で既存の Sprint 1 / Sprint 2 と同等以上の規模。共有側も「発行・入力・期限・再ロック・不正検知・永続化の分離」で独立した契約が20項目近くになる。1本にまとめると契約が40項目を超え、部分的な完成を「完了」と誤認しやすい |
| **審査提出の固定点を先に置きたい** | 教訓6により、ストア画面に表示した商品は初回審査で全部提出する必要がある。商品ラインナップの確定は後戻りコストが大きいので、共有機能という不確定要素を同居させず、Sprint 3 の完了をもってラインナップを凍結する |

これに伴い、既存ロードマップの「Sprint 4: リリース準備」は **Sprint 5 に繰り下げる**（`docs/spec.md` のロードマップ表も更新済み）。

#### Sprint 3 に含めるもの

| 含めるもの | 理由 |
|---|---|
| パックのデータモデルと有料パックのお題データ | 売る中身がなければ課金は成立しない。かつ「パックという単位」は Sprint 4 の共有機能の土台でもある |
| ストア画面（一覧・購入・復元） | 購入の復元は iOS / Android 両ストアの必須要件。画面がないと審査に出せない |
| RevenueCat 連携 | spec.md で課金基盤として指定済み。前作 `apps/mobile/lib/iap.tsx` のパターンを踏襲する |
| スタート設定画面のパック選択 | 買ったパックで遊べなければ課金の意味がない。購入と利用が1周してはじめて「マネタイズが成立した」と言える |

#### Sprint 3 から外すもの

| 外すもの | 理由 |
|---|---|
| パックの一時共有機能（コード発行・入力） | 上記の理由で Sprint 4 に分離 |
| 実機・ストアコンソールでの実購入テスト | EAS Dev Build と両ストアの商品登録が前提で、Evaluator（Playwright / Expo Web）では検証不能。リリース準備（Sprint 5）で実機確認する。本スプリントでは「キー未設定時の安全な振る舞い」と「所有状態を注入したときの表示・挙動」を検証対象にする |
| アイコン・スプラッシュ・プライバシーポリシー・ストア掲載情報 | Sprint 5 |
| ハイスコア、効果音、触覚フィードバック | spec.md で優先度「低」 |

#### 初回ラインナップの決定

有料パックは **4つ（旅行 / ビジネス / 動物 / 食べ物）** を初回ラインナップとする。spec.md の想定テーマは「旅行、ビジネス、日常会話、動物、スポーツ、食べ物 **など**」と例示であり、日常会話は無料スターターパックが担っているため重複を避けた。スポーツ等の追加は将来の別リリースで行う（その際も、追加分をまとめて審査提出する前提で扱う）。

### Generator への実装指針

本スプリントは Evaluator が Expo Web（Playwright）で検証する。実決済（Apple / Google Pay）は検証できないため、**次の2点を満たす設計にすること**。設計の詳細（ファイル配置・状態管理の方式）は Generator の裁量。

1. **APIキー未設定時に安全に止まること**
   `EXPO_PUBLIC_REVENUECAT_IOS_KEY` / `EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` が未設定の環境では、購入・復元の操作で「準備中」の主旨のメッセージを出して何もしない（前作 `iap.tsx` と同じ方針）。`react-native-purchases` は Expo Web にネイティブ実装がないため、**Web で import しただけでクラッシュしない**形にすること。

2. **所有状態を外から注入できること**
   「どのパックを所有しているか」の判定を RevenueCat の呼び出しから切り離し、所有パックID集合を外部から与えられる口（テスト用フック、デバッグ用ストレージキー等、手段は問わない）を用意する。これがないと Evaluator は購入後の画面・パック選択・出題を一切検証できない。Sprint 4 の一時解放も同じ層に乗るため、ここを疎結合にしておくことが次スプリントの前提になる。

その他、教訓集から本スプリントに効くもの:

- エラーメッセージには常に短いエラーコードを添える（RevenueCat 起因は `RC-<code>`、独自ロジック起因は `APP-01` のような連番）。開発中だけ詳細を出す運用はしない（教訓9）
- 商品の購入は `purchaseProduct(productId)` ではなく `getOfferings()` → `availablePackages` から該当パッケージを探して `purchasePackage(pkg)` を呼ぶ方式に統一する（Android で `PRODUCT_NOT_AVAILABLE_FOR_PURCHASE_ERROR` を踏むため）
- 商品IDは iOS / Android で同一。パック定義の1箇所にだけ書き、画面側にハードコードしない

### 実装する機能

- **機能A: パックのデータモデルとテーマ別お題データ**
  `packages/game-core` にパックの型を定義する。各パックは識別子、表示名、テーマの絵文字、収録問題数、無料/有料の別、有料なら商品IDと価格（円）を持つ。既存の無料スターターパック（30問）を新モデルに載せ替え、有料パック4種（旅行 / ビジネス / 動物 / 食べ物）をそれぞれ100問以上のカードで追加する。カードの規約（説明文8〜20語、お題の英単語を含めない、短文と長文を混在させる）は Sprint 1 と同一とし、**全パック横断で自動テストできる**形にする。

- **機能B: RevenueCat 連携**
  前作 `apps/mobile/lib/iap.tsx` のパターンを踏襲し、アプリ全体に所有パックの状態を配るプロバイダを実装する。起動時に購入状態を取得し、購入・復元の操作を提供する。APIキー未設定時は「準備中」で安全に停止する。エラーは短いエラーコード付きで表示する。

- **機能C: ストア画面**
  `/store` を追加し、全パック（無料含む）をカード一覧で表示する。各カードにパック名・テーマ絵文字・収録問題数と、状態に応じた表示（STARTER / 購入済み / 価格つき購入ボタン）を出す。「購入を復元する」とホームへ戻る導線を置く。ホームからストアへの導線を追加する（Sprint 2 で「押せないプレースホルダーは置かない」としていた入口を、ここで実体のあるものとして開通させる）。

- **機能D: スタート設定画面のパック選択**
  スタート設定画面に、制限時間・スクロール速度に続く3つ目の選択肢としてパック選択を追加する。未所有の有料パックはロック表示にし、選ぼうとするとストアへ誘導する。所有しているパックを選んで開始すると、そのパックのカードだけが出題される。確認パネルにも選択中のパック名を表示する。

### スプリント契約（完了条件）

以下の全条件を満たした場合のみ、このスプリントは完了とする。

**パックのデータモデルとお題データ（機能A）**

- [ ] `packages/game-core` にパックの型と全パックの一覧が定義され、各パックが「識別子 / 表示名 / テーマ絵文字 / 収録問題数 / 無料か有料か / 有料なら商品IDと価格（円）」を持つ
- [ ] 有料パックが4つ以上存在し、それぞれ100問以上のお題カードを持つ。無料スターターパックは30問以上のまま残っている
- [ ] 全パックのカードを横断して検証する自動テストが存在し、「説明文が8語以上20語以下」「説明文にそのお題の英単語（単純な複数形・活用形を含む）が含まれない」「同一パック内でお題単語が重複しない」の3点が全カードで満たされることを確認できる
- [ ] 有料パックの商品IDはパック定義の1箇所にのみ記述され、画面コードにハードコードされていない。iOS / Android で同じ文字列が使われる
- [ ] RevenueCat のキーが未設定の状態でも、無料スターターパックを選んでゲームを最後まで遊べる

**ストア画面と課金（機能B・機能C）**

- [ ] ホーム画面に「ストア」への導線があり、タップするとストア画面が表示される
- [ ] ストア画面に全パック（無料含む）が一覧表示され、各カードにパック名・収録問題数・状態（STARTER / 購入済み / 価格つき購入ボタン）が表示される。未所有の有料パックにのみ購入ボタンが出る
- [ ] ストア画面に「購入を復元する」導線と、ホームに戻る導線の両方が存在する
- [ ] RevenueCat APIキーが未設定の環境で購入ボタンを押すと「準備中」の主旨のメッセージが表示され、アプリがクラッシュせず画面も操作可能なまま維持される
- [ ] RevenueCat APIキーが未設定の環境で「購入を復元する」を押しても同様に「準備中」の主旨のメッセージが表示され、クラッシュしない
- [ ] Expo Web でホーム・ストア・スタート設定・プレイの各画面を一巡しても、課金モジュール由来の未処理例外がコンソールに出ない
- [ ] 購入失敗時・復元失敗時に表示されるメッセージには、`RC-` または `APP-` で始まる短いエラーコードが含まれる
- [ ] 購入処理中は該当パックのボタンが処理中の表示に変わり、連打しても購入処理が二重に開始されない
- [ ] 所有パックを外部から注入する手段が存在し、それで特定の有料パックを所有状態にすると、ストア画面のそのパックの表示が購入ボタンから「購入済み」に変わる

**パック選択（機能D）**

- [ ] スタート設定画面でプレイするパックを選択でき、確認パネルに選択中のパック名が表示される
- [ ] 何も所有していない状態では無料スターターパックが既定で選択されており、有料パックはロックされていると分かる表示になっている
- [ ] 未所有の有料パックを選ぼうとしても、そのパックでゲームが開始されない（ロックのまま選択されないか、ストア画面へ誘導される）
- [ ] 有料パックを所有状態に注入すると、スタート設定画面でそのパックを選択でき、ゲームを開始できる
- [ ] 有料パックを選んで開始したゲームでは、出題されるお題カードがすべてそのパックに属するものであり、他パックのカードが混ざらない
- [ ] パックを切り替えて新しいゲームを開始すると、前回のパックの出題状態（出題済みカードの記録など）が引き継がれず、選択したパックの先頭から出題が始まる

**堅牢性・回帰**

- [ ] 幅375pxのビューポートで、ストア画面の全パックカード・復元導線・戻る導線にスクロールで到達でき、横スクロールが発生しない
- [ ] 幅375pxのビューポートで、スタート設定画面に制限時間・速度・パックの3つの選択肢と確認パネルがすべて収まるか縦スクロールで到達でき、横スクロールが発生しない
- [ ] Sprint 1 および Sprint 2 の契約が引き続きすべて満たされている（カウントダウン、単語数と速度選択に応じた流れる説明文、CORRECT / SKIP の加点、猶予時間と自動スキップ、タイマー0でのリザルト遷移、遊び方画面、リザルトの称賛メッセージ・正答率、レビュー訴求のカウント蓄積が回帰していない）
