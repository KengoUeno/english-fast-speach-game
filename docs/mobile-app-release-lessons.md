# モバイルアプリ(App内課金・iOS/Android・複数パッケージ)公開ナレッジ

察してEnglish(taboo-english-game)のExpo/EAS Build/RevenueCat構成での初回ストア公開(2026年8〜9月)で得た教訓。

**このファイルを参照すべき条件**: 新しいアプリが以下に当てはまる場合、着手前に必ず読むこと。
- App内課金(IAP)がある
- iOS/Android両方にリリースする
- 有料コンテンツパッケージが複数ある(単一商品ではない)

## 開発着手前にやること

- [ ] Google Playの新規アカウントは「クローズドテスト12人×14日間」が本番リリースの必須条件。開発開始と同時にテスター候補のあてを探し始める(この工程が一番時間がかかるボトルネックになる)。
- [ ] モバイルが主目的なら最初からExpoでプロジェクトを始める(Webから後で移植すると二度手間)。
- [ ] RevenueCat等のAPIキー・環境変数は、最初のproductionビルドを走らせる前に本番用の値まで確定させる。
- [ ] iPad/タブレット対応(`supportsTablet`)は、対応する気がなければ最初からfalseにしておく。
- [ ] ストアに1つでも商品を出すなら、Apple側は審査提出の前提として「フルの店頭情報(スクリーンショット・説明文・価格・年齢制限など)」が必要になる、と最初から見積もりに入れる。
- [ ] プライバシーポリシー/サポートURLのホスティングは、Web版を作らない(モバイルのみの)構成ならVercelではなく**GitHub Pages**を使う。アプリのリポジトリに直接置け、追加のアカウント・ダッシュボードが不要になる(察してEnglishはWeb版が先にあったのでVercelを使ったが、それは今回限りの事情)。

## 教訓

### 1. Webから移植するより、最初からExpoで作る
Next.jsのWebアプリを先に作り、あとからモバイル版をExpo(React Native)へ移植する流れは二度手間になった。UIの確認は `npx expo start --web` でReact Native Web経由の通常ブラウザ表示を使えば、Webアプリと同じ感覚でホットリロードしながら確認できる。実機の触り心地を見たい時だけExpo Go、ネイティブ機能(課金など)を試したい時だけEASの開発ビルド、と使い分ける。

### 2. Expo Goには「動かせる範囲」がある
Expo Goはreact-native-purchasesのようなカスタムネイティブモジュールを含むアプリを実行できない(Expo SDK標準搭載モジュールのみ対応)。課金などストア固有の機能検証は、Expo Goを経由させずEASの開発ビルドか実際のストアの実機テストに直接進む。

### 3. 環境変数はビルドの前に確定させる
EAS Buildの環境変数(`EXPO_PUBLIC_...`)はビルド時にJSバンドルへ焼き込まれる。後から値を更新しても既存のバイナリには反映されず、実機で「Wrong API Key」のような症状が出る。本番キーを含む環境変数は、最初のproductionビルドを走らせる前に必ず確定させる。切り替えた場合は迷わず作り直す。

### 4. バージョンコードはトラックを跨いで使い回せない
Google Playは同一アプリ内でversionCode/buildNumberの再利用を許可しない。動作確認済みのリリースを別トラック(内部テスト→クローズドテストなど)にも展開したい時は、新規リリース作成でファイルを再アップロードするのではなく「プロモート」機能で昇格させる。新規作成が必要なのは中身を変える時だけ。

### 5. 外部要因の失敗は焦って直さない
Androidビルドが `Gradle build failed` になり、ログを追うとMaven Central側の `429 Too Many Requests` が原因だった、ということがあった。ビルド失敗時はまずログの実際のエラー箇所を確認する。外部インフラのレート制限であれば、設定をいじらずに時間を置いて再試行するのが正解。

### 6. 【重要・要修正】Appleは画面上の商品を「全部まとめて」審査に出す必要がある
当初「最初の1つだけバージョンと同時提出すれば、Sandboxでの動作確認だけは全商品できるようになる(実機で確認済み)」と記録していたが、これは**Sandboxテストが通ることと、審査に通ることは別**という点を見落としていた。実際には、ストア画面(UI)に5つのパックを表示していたのに審査には1つ(食べ物パック)しか含めていなかったため、"Guideline 2.1(b) - Performance: App Completeness"で却下された。Appleのメッセージ: 「the app includes references to word pack but the associated In-App Purchase products have not been submitted for review」。

**Rule**: アプリの画面に表示されている全てのApp内購入商品は、最初の審査提出の時点で**全部まとめて**含める。「1つだけ先に出して後から個別に追加すればいい」という判断はしない(Sandboxテストが通っても審査に通る保証にはならない)。

### 6b. App Store Connectで複数のApp内購入を1つの提出にまとめる手順
上記をやり直す際、UIの挙動が分かりにくく時間を溶かした。手順を残す。

- 新しく作成したApp内購入商品は、それぞれ**自動的に個別の「提出物の下書き」(1商品だけ)**を持つ。
- 「アプリ内購入」一覧ページの「編集」→チェックボックスは、**既に個別の下書きに紐づいている商品は選択できない(グレーアウトする)**。ここで詰まりやすい。
- まとめるには、各商品の詳細ページを開き、「この項目は審査用に追加されていますが、**項目を削除することは可能です**」のリンク(または下書きパネル内の赤い「−」ボタン)から、個別の下書きを削除する。商品自体は消えず、単に「どの提出物にも属さない自由な状態」に戻るだけ。
- 対象の商品(1回のリリースでUIに表示する全商品)を全部この「自由な状態」にしたら、改めて「アプリ内購入」一覧のチェックボックスで全部選択し、「審査用に追加」をクリック → 1つの複数商品セットの下書きができる。
- アプリバージョンのページ(却下済みで編集可能な状態、または新規バージョン)で「審査用に追加」からこのセットを選んで紐付け、まとめて審査提出する。
- 既にどれかの商品が却下済みのバージョンに紐づいている場合は、先に「App Review」→ 該当の提出物の詳細ページ →「提出をキャンセル」→「確認」で取り下げる。これで商品・バージョン両方が自由な状態に戻り、上記の手順をやり直せる。

### 7. ストア掲載情報の重さを見積もり損ねない
「購入テストがしたいだけ」でも、Appleの審査提出には店頭情報一式が必要になる。スクリーンショットはGoogle Playと違い厳密なピクセルサイズ指定(例: 1242×2688)で、Google Play用素材は流用できない。iPad対応を外し忘れると13インチiPad用の追加素材要求も発生し、そのためだけに再ビルドが必要になる。マーケティング素材は最初から両ストアの正確なピクセル要件で作る。

### 8. 個人情報を公開する設定は一呼吸置く
EU向けのデジタルサービス法(DSA)対応フローなど、「入力すると公開されます」と明記されたフォームが出てくることがある。既存のアカウント設定(コンプライアンス欄など)で同じ内容がすでに満たされていないか確認してから入力する。分からなければ埋める前に立ち止まって確認する。

### 9. エラー表示には常に短いコードを添える
「購入に失敗しました。しばらくしてからもう一度お試しください。」のような汎用メッセージだけだと、原因調査に時間がかかる。開発中だけ詳細表示してリリース前に消す、という運用は削除し忘れるリスクがあるのでやらない。代わりに `(RC-5)` のような短いエラーコードを恒常的にUI上に残す(RevenueCat等SDK起因は`RC-`+エラーコード数値、独自ロジック起因は`APP-01`のような連番)。

### 10. ストア評価ポップアップ(ネイティブレビュー依頼)はTestFlightでは出ない
`SKStoreReviewController`/`expo-store-review`のレビュー依頼は、実際のApp Store経由でインストールされた本番版でのみ動作する。TestFlightのベータ版では意図的に無効化されるため、TestFlightでの実機テストで出なくても実装ミスとは限らない。Androidも同様にGoogle Play側の非公開クォータがあり、条件を満たしても毎回確実に出るわけではない。動作確認は本番リリース後にしかできない前提で実装する。実装のタイミングは「ネガティブな瞬間を避け、ある程度使い込んだ後」(例: 3回セッション完了後、かつ前回表示から60日以上)にする。

## 技術的な補足

- **Android実機での商品購入解決**: `Purchases.purchaseProduct(productId)`(商品IDを直接指定する方式)はAndroidで`PRODUCT_NOT_AVAILABLE_FOR_PURCHASE_ERROR`になることがある。`Purchases.getOfferings()`でOfferingを取得し、`availablePackages`から目的の`product.identifier`に一致する`PurchasesPackage`を探して`Purchases.purchasePackage(pkg)`を呼ぶ方式で統一する。
- **UI確認の使い分け**: 日常のUI確認は`expo start --web`、実機の触り心地はExpo Go、ネイティブ機能(課金等)の検証はEASの開発ビルド(`--dev-client`)。
- **ビルド手段**: Xcode/Android Studioのローカルインストールは不要。`eas build --platform ios|android`がクラウド上のMac/Linuxマシンでコンパイル・署名まで行う。App Store Connect/Google Play Console側のストア掲載作業(スクリーンショット・説明文・IAP登録・審査提出)は、ビルド手段によらず必ず手動(ブラウザ操作)で行う必要がある。

## 実際のビルド履歴(なぜ何度もビルドが発生したか)

| プラットフォーム | バージョン | 結果 | 原因 |
|---|---|---|---|
| Android | versionCode 3 | 失敗 | Maven Centralの429レート制限 |
| Android | versionCode 4 | 失敗 | Maven Centralの429レート制限(再発) |
| Android | versionCode 5 | 成功 | 一晩待って再試行 → 本番APIキーで内部テストに使用 |
| Android | versionCode 6 | 成功 | クローズドテストに5が使えず作り直し(プロモート未使用) |
| iOS | build 3 | 購入失敗 | Paid Applications Agreement未有効化 |
| iOS | build 4 | 提出不可 | 正しいAPIキーで作成 → 13インチiPad用スクリーンショット要求で審査提出がブロック |
| iOS | build 5 | 審査提出 | supportsTabletをfalseに変更 → 無事提出、Sandbox購入も成功 |
| iOS | build 6 | 却下 | Guideline 2.1(b) App Completeness — 画面に5パック表示しているのに1つしか審査提出していなかった |
| iOS | build 7 | 審査提出 | 5商品全部を1つの提出にまとめ直し、新しいバイナリと一緒に再提出 |

理想的には、最初から本番キー・iPad非対応・完成した店頭素材・**画面に表示する全商品を最初から審査に含める**、を用意しておけば、ビルドは1〜2回で済んだはず。
